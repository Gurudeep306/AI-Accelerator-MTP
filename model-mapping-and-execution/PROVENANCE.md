# Where every input came from

Three kinds of number appear in the output, and every section of
`out/simulation_output.txt` is labelled with which kind it is.

| Label | Meaning |
|---|---|
| **TRACED** | Produced on your machine by executing the detector |
| **SIMULATED** | Produced on your machine by SCALE-Sim, cycle by cycle |
| **MEASURED** | Produced by someone else, copied in, never recomputed here |

---

## The inputs

### `src/mdl/` — the detector source

`gelan_anytime.py`, `common.py`, `detect_head.py`, `postprocess.py`.

**Not written here and not modified.** These are the files from the anytime
detector project, copied verbatim. The only addition is an empty `__init__.py`
so Python can import them as a package, because the originals use relative
imports (`from .common import Conv`).

Everything labelled TRACED comes from executing these files. If you want to
prove they are unmodified, diff them against the originals in the project folder.

What they feed: the convolution count, the multiply-add totals, every tensor
shape, the per-stage split, the peak activation set, the figures at all five
input sizes.

### `inputs/accelerator_workload.csv` — the shipped layer table

**Not produced here.** It comes with the detector project, one row per
convolution, generated by its own `make_accelerator_workload.py`.

This file is used for exactly one thing: step 2 compares the trace against it,
field by field, as a check. **No number from this file reaches any result
table.** If the check fails the run stops. The point of including it is to show
that a workload recovered by execution and a workload recorded by its author
agree on all 1,208 compared fields.

### `inputs/measured_accuracy.json` — the accuracy column

**Measured, not simulated.** Copied from `PROJECT_EXPLAINED.md` sections 8.1,
8.3 and 8.4, which record the evaluation of checkpoint
`runs/anytime_interrupt/train6_bdd70k/last.pt`.

- per-head mAP50, mAP50-95, precision and recall on 1,500 unseen images
- per-class box counts and AP50 across the 65,000-image training split

Every key in that file carries a `_source_section` pointing at where it came
from. Nothing in this package can produce these numbers, because the trained
weights are not included. They feed sections G and H, and only those.

### `inputs/platform.json` — the target board

**Measured and published specification, not simulated.**

- The part figures (220 DSP slices, 140 block memories, DDR3L at 1066 MT/s)
  are the published specification of the Xilinx XC7Z020 on a Digilent Zybo Z7-20.
- The built-design figures (80 DSP slices used, 64 of them the array, 11,057
  LUTs) come from a yosys synthesis run against that part.
- The 60.1 per cent array utilisation comes from the Verilog testbench of the
  accelerator, on a schedule of 8 weight-load cycles followed by 16 compute
  cycles.

The derating factor in section D is the ratio of the cycle model's predicted
utilisation to that measured 60.1 per cent. It is the only place a measured
hardware number enters a simulated latency, and section D prints both halves of
the ratio so it can be checked.

## The code that produces results

### `src/sim_one.py`, `sim_shapes.py`, `sim_expand.py` — SCALE-Sim

**Every latency in this package comes from here, and nothing is modelled.**
SCALE-Sim is a published cycle-level simulator for systolic arrays. It is
installed from the source repository at a pinned commit rather than from PyPI,
because the released package is behind the repository, and the run header prints
the commit.

`sim_one.py` runs one layer shape and caches the result. `sim_shapes.py` covers
every distinct shape in a configuration. `sim_expand.py` totals SCALE-Sim's
per-layer cycles over a stage, or over the stages an answer needs. The only
arithmetic applied to a simulated number anywhere in this package is addition.

Three things about how it is driven are worth stating plainly, because each one
is a decision that could have been made badly:

- **One process per shape.** SCALE-Sim does not release memory between the
  layers of a single call. Over 151 layers the resident set climbs past two
  gigabytes and the operating system kills the process with no traceback, which
  reads as "the simulator cannot do this" and tempts you into a model. It can;
  it just has to be handed the work in pieces.
- **Shapes, not layers.** The four detection heads are identical in structure,
  so 151 convolutions cover 37 distinct shapes. Each is simulated once. This is
  a reuse of results, not an approximation, and it is checked two ways: repeated
  shapes are compared against each other, and one configuration is simulated
  layer by layer in place with no reuse and compared against the cache. Both
  checks are reported in section J, and a non-zero count there would invalidate
  the method rather than being something to work around.
- **Padding.** SCALE-Sim convolves without implicit padding while the detector
  pads to preserve resolution, so each input map is enlarged by `k − 1` before
  being handed over. Without that the two disagree by about seven per cent on
  the multiply-add total alone.

The one place a measured hardware number touches a simulated latency is the
derating in section D, which scales simulated cycles to the utilisation measured
in the accelerator's own Verilog. Both halves of the ratio are printed.

## What this package deliberately does not claim

**Sparsity is not simulated.** It needs the trained weights and real
activations. The latencies are therefore upper bounds in that respect.

**Accuracy does not move with hardware settings.** In reality a reduced numeric
precision would change it, which would make the operating-point table
two-dimensional. Quantifying that needs a calibration run against the trained
checkpoint.

**Post-processing is excluded.** Decoding and non-maximum suppression run over a
fixed grid of 8,400 candidates per head regardless of scene content, so the cost
is bounded and content-independent, but it is not zero and it is not modelled.

**The derating factor is assumed to hold at other array sizes.** It was measured
at one size on one schedule.
